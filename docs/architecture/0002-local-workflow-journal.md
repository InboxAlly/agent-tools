# 0002: The local workflow journal drives recovery state

Status: accepted client decision, 2026-09-18. Local behavior only; no backend dependency.

## Decision

Each allocated run keeps a small append-only journal of workflow observations, written by
`placement note`. The run's `state` is the allocation lifecycle until the first entry
(`prepared`, `allocation_unknown`, `allocated`) and afterwards exactly the state of the
last journal entry. `placement runs` reports that state so an agent resuming after a
restart can pick the safe next action from specification section 14 without relying on
conversation memory.

Events are the post-allocation states of section 14 plus the two approval observations:

| Event | Resulting state | Reason |
| --- | --- | --- |
| `awaiting_import_approval`, `import_outcome_unknown`, `import_verified`, `awaiting_send_approval`, `send_outcome_unknown`, `send_confirmed`, `watching`, `done`, `stopped` | The same name | These are states |
| `import_approved` | `import_outcome_unknown` | Once approval is recorded, the import may happen at any moment. If the process dies before `import_verified`, the only safe recovery is to inspect the exact list and full membership before acting |
| `send_approved` | `send_outcome_unknown` | Once approval is recorded, the send may happen at any moment. Until `send_confirmed`, recovery must inspect send history and result evidence and must never resend |

A note cannot claim `prepared`, `allocation_unknown`, or `allocated`; the CLI owns those.
`status` and `watch` persist result snapshots without changing the workflow state.

## What a note validates

- The test ID selects exactly one saved run with a validated manifest.
- Details may contain only `platform`, `workspace_label`, `from`, `subject`, `list_name`,
  `recipient_count`, `esp_object_id`, `observed_at`, and `note`, with type and size limits and
  no control characters. Any other key, including credentials or campaign bodies, is rejected.
  The details file is limited to 16 KiB.
- An approval must record what was approved: `import_approved` needs `list_name` and
  `recipient_count`; `send_approved` needs `from`, `subject`, `list_name`, and `recipient_count`.
  Approval details must match the immutable intent and manifest (`APPROVAL_MISMATCH`, exit 5).
  Other events may record a mismatch, for example the observed sender before `stopped`.
- Send-oriented events (`awaiting_import_approval`, `import_approved`, `awaiting_send_approval`,
  `send_approved`) are refused once the send window has expired (`SEND_WINDOW_EXPIRED`, exit 8).
  `send_approved` additionally requires the proposed 120-second minimum remaining window from
  specification 11.5 (`SEND_WINDOW_INSUFFICIENT`, exit 8). Outcome events remain recordable.
- The timestamp is generated by the CLI. The evidence type is declared by the caller.

## What it does not prove

The journal is a recovery aid, not proof of consent or of a remote mutation. An approval
entry never authorizes an action after context changes; the skill must re-show and
re-confirm current details. `tool_observed` versus `user_reported` records how the agent
learned something, which the CLI cannot verify. The journal never contacts the API.

## Persistence and compatibility

Run files move from `local_schema_version` 1 to 2. Version 1 files load with an empty
journal and are rewritten as version 2 on the next save. Loading rejects a file whose state
disagrees with its journal, whose entries are out of sequence, or whose workflow state has no
allocation. Older development builds reject version 2 files as `STATE_INVALID` rather than
misreading them. The journal holds at most 200 entries (`JOURNAL_FULL`).

## Related resume rule

`placement resume` recovers only a request whose creation was attempted. On a `prepared`
request it returns `REQUEST_NOT_STARTED` (exit 2) without touching the network; a process
restart never turns an intent into an allocation. `placement create` makes the first attempt
or replays it under the same persisted key.
